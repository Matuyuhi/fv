## 0. 位置づけ

fv に「ファイルを跨いで探す」機能が無かった (`/` はファイル内限定)。インデックス設計の議論
(#index-design) の結論は次の通りで、この実装はその **1 段目** にあたる。

1. インデックス無しの横断 grep を入れて、大きめの repo で手触りを確かめる (済)
2. **content cache (読んだ内容をメモリに残す) + 完走した走査のファイル一覧 (corpus) の使い回し** ← 今ここ
3. それでも足りなければ trigram 等の本物のインデックス
4. 永続化は最後

2 段目へ進んだ根拠は §5 の実測: 1 段目の残りコストは **walk 19ms + read 19ms + 照合 2ms**
(2 万ファイル・120MB) で、ほぼ全部が syscall だった。照合を速くしても何も変わらないので、
syscall の側を「変わっていなければ払わない」形にした。

「インデックス無し」で先に入れる理由は、大きい repo で遅くなる主因が **照合ではなく走査と
読み込み** であり、そこは並列 walker + ストリーミングで作りを正しくすれば ripgrep 相当まで
行けるから。逆に、素朴な逐次 grep で入れてしまうと「遅いのはインデックスが無いからか、
作りが悪いからか」が切り分けられず、手触りの評価自体が成り立たない。

そのため最初から次の 4 点を満たす形で作った (どれか 1 つでも欠けると評価がずれる):

| 要件 | 実装 |
| --- | --- |
| 並列走査 | `ignore::WalkBuilder::build_parallel` (ripgrep と同じ walker、新規依存なし) |
| 結果のストリーミング + 打ち切り | 1 ファイル = 1 メッセージで channel へ流し、クエリが変わったら `AtomicBool` で止める |
| バイナリ・巨大ファイルの除外 | 先頭 8KB に NUL / 8MB 超は読まない |
| ヒット数の上限 | 全体 5000 件 / 1 ファイル 200 件で走査ごと打ち切り、タイトルに `truncated` |

## 1. 構成

```
src/component/grep/
  search.rs   走査本体 (背景スレッド側)。クエリ → Receiver<Message>
  mod.rs      GrepState: クエリ・デバウンス・結果 (パス順)・選択・stale
  view.rs     オーバーレイの描画 (Finder と同じ形。画面に映る行だけ ListItem を組む)
```

- `Mode::Grep` は **unit variant** で、状態は `App.grep: GrepState` に常駐する。
  Finder (`Mode::Finder(Finder)`) と違って Mode の中に持たせないのは、オーバーレイを閉じても
  走査を続け、次に開いた時に前回の結果をそのまま見せるため (大きい repo で同じクエリを
  何度も歩き直さない)。「状態の持ち主は誰か」という意味では `App.file_index` (Finder の候補
  の背景走査) と同じ側にいる
- キールーティングは `Mode::Finder` の直後 (app/keys.rs `on_key`)。開くキー `Ctrl+f` は
  `Ctrl+p` と同じ位置 (レーン・フォーカスを問わない、EDIT 中は届かない)
- ヒットを開く (`open_grep_hit`) は `open_selected` → `Viewer::locate_search` の 2 段。
  GIT レーンに居た場合は `enter_lane(0)` で VIEW に戻してから開く (open_selected は GIT だと
  diff を開いてしまうため)
- 描画は `shell::draw` から `grep::view::draw_grep(frame, &mut app.grep, full)`。
  「View は自分の状態しか受け取らない」規約通り `&App` は渡さない

## 2. 走査 (search.rs) の詳細

### 2 つの経路と、どちらを使うかの判定

| 経路 | いつ | 払うもの | 払わないもの |
| --- | --- | --- | --- |
| `spawn_walk` | 初回 / 監視が無い / 構造が変わった (作成・削除・リネーム・取りこぼし) | walk + stat + **変わったファイルの read** | 変わっていないファイルの read |
| `spawn_corpus` | 監視が生きていて、前回の完走以後に構造の変化が無い | **メモリ上の照合だけ** (+ 内容が変わったと通知されたファイルだけ stat + read) | walk・stat・read |

判定は `GrepState::start_job` の 1 箇所: `watched && snapshot.trusted`。`trusted` が立つのは
**走査を起こした時点と完走した時点の両方で FS 監視が生きていた** 時だけ (`Job::watched` と
`GrepState::watched`)。監視が無い間に起きた変更は誰にも分からないので、その間の一覧は使わない。
落とすのは:

- 構造の変化の通知 (`invalidate`) — どのパスがあるかが変わったので歩き直す
- 内容だけの変化 (`touch(path)`) で **一覧に無いパス** — 取りこぼしの可能性があるので歩き直す側に倒す
- 走査中に来た通知 — その走査は変更の前後どちらを読んだか分からないので `Job::watched = false`
- 監視が途切れた (`set_watched(false)`)
- 走査条件の切替 (`set_options`) — 一覧そのものを捨てる
- 無視設定の変更 — 各階層の `.gitignore` / `.ignore` と `.git/info/exclude` は watch.rs が
  (隠しファイルでも) 常に structural として通す。root の外の global gitignore
  (`core.excludesFile`) は監視が届かないので、走査を起こす時点の (mtime, size) を snapshot に
  添え、次に使い回す前に照合する (`global_ignore_stamp`)

`touch(path)` で一覧にあるパスなら、その項目だけ `dirty` にして一覧は使い続ける (AI が 1 ファイルを
書き換え続ける状況で、そのたびに歩き直さないため)。dirty な項目は次の照合で **stat を見ずに必ず
読み直す** — 同じ大きさで mtime の粒度内に書き換えられた場合、stat では変わっていないように
見える。通知で確定した変更を stat の推測に戻さない。読んだ結果は cache に反映するとともに
`Message::Refreshed` で一覧へ書き戻して dirty を消す (消さないと変更されたファイルが単調に増え、
毎回それら全件を読み直すことになる)。走査中に通知が来た走査 (`Job::changed_during`) の
Refreshed は捨てる — 読んだ後に来た変更の dirty を消してしまうため。

監視側 (watch.rs) の変更: `FsWatcher::is_active` (登録が終わって以後の変更が必ず届く状態か) と、
inotify のキュー溢れ (`Event::need_rescan`) を `Change::overflow` (「何が変わったか分からない」、
path は root、structural) として通すようにした。後者は以前は黙って捨てていた — ツリーの再走査には
害が無かったが、一覧を信用する根拠には穴になる。overflow はビューア側でも path 単位の後始末では
足りない (取りこぼした変更が表示中のファイルだったかもしれない) ので、cache を全部捨てて表示中の
ファイルを読み直す。

### content cache (`Cache`)

`(path → Entry { mtime, size, content })` の HashMap を GrepState が持ち、走査スレッドと `Arc` で
共有する。`content` は Text (読んだ Vec をそのまま持つ・写しは作らない) / Uncached (上限
`MAX_CACHE_BYTES` = 256MB に収まらなかった。毎回読む) / Skip (バイナリ・8MB 超。読まない印) の
3 種。Skip も残すのは、次から stat だけで飛ばせるため。

**走査中はファイルごとにロックを取らない**。map は不変のスナップショット (`Arc<Map>`) として
ワーカーへ配り、読み直した項目はワーカーの手元 (`Seen`、`Box<dyn FnMut>` が捨てられる時に流す)
に溜めて、走査の終わりに 1 回で差し替える (`Cache::replace`)。完走したなら seen だけの map に
する (消えた・無視対象になったファイルはここで落ちる)、途中で止まったなら前の map に重ねる。
最初は per-file の `Mutex<HashMap>` + `Arc::from(&buf)` の写しで作っていたが、cold の走査が
2 倍 (41ms → 80ms) に遅くなり、ロック 3 回 + memcpy を消して 54ms まで戻した。上限の判定は
`AtomicUsize` の予約で、読み取りだけで弾ける時は RMW を発行しない。読んでいる間に伸びた
ぶんは追加で予約し、収まらなければ Uncached に戻す。

**走査は同時に複数走りうる** (キャンセルは join しない)。古い走査が新しい走査より後に終わって
map を差し替えると、新しい走査が読んだ版が古い版に戻る。そこで cache は世代 (`Cache::begin`)
を持ち、差し替え (`replace`) は世代の判定と map の入れ替えを同じロックの中で行って、古い世代は
「完走扱いにしない + map に無いパスだけ足す」に降格する。予約の会計 (`bytes`) は差し替えで
正確な値に置き直すので、古い走査の `release` は飽和減算で 0 で止める (ずれは次の差し替えで消える)。

残る cold の差 (41ms → 54ms、cache の保持込みで 70ms 台) は stat と、120MB を新しく確保する
page fault。初回に 1 度払うだけで、以後は walk 経路で読まなくなるぶん (33ms) と corpus 経路
(10ms) で回収する。

### 使い続けた時のメモリの上限

| 持ち物 | 上限 | 根拠 |
| --- | --- | --- |
| cache の本文 (Text) | `MAX_CACHE_BYTES` = 256MB | 予約カウンタ。超えたぶんは Uncached (毎回読む) |
| cache の項目数 | 今あるファイル数 | 完走のたびに seen だけで map を作り直す。消えたファイルが残るのはキャンセルされた走査の間だけ |
| snapshot の一覧 | cache と同じ Arc | 二重に持たない。dirty にした項目は本文を手放す (`without_content`) |
| 結果 (`files`/`rows`) | `MAX_HITS` 5000 件 + 1 ファイル 200 件、行は 400 char で切り出し | 従来通り |
| キャンセル時の map 複製 | 読み直した項目が 1 つでもある時だけ | 打鍵のたびに 10 万項目を複製しない (`Cache::replace`) |

### 打ち切り後も歩き続ける

`MAX_HITS` を跨いだら `Done { truncated: true }` を **その場で** 送り、ヒットの送出は止めるが、
キャンセルされない限り walk 自体は最後まで続けて `Corpus` を送る。「fn」のような広いクエリから
打ち始める使い方では、打ち切りで止めていると一覧がいつまでも揃わないため。`GrepState::busy` は
Done で false になる (タイトルの `searching...` は消える) が、`job` は Corpus か Disconnected
まで残す。

### スレッド構成

```
UI スレッド ── spawn() ──▶ ランナースレッド ── walker.run() ──▶ ワーカー N 本 (ignore が起こす)
     ▲                            │                                     │
     │  Receiver<Message>         │ Done (完了時 1 回)                    │ File (ヒットのある
     └────────────────────────────┴─────────────────────────────────────┘  ファイルごと 1 回)
```

`WalkParallel::run` は内部でワーカーを複数起こしたうえで **呼び出し側をブロックする** ので、
それ自体をもう 1 本のスレッドへ出している (UI スレッドを止めない)。ワーカー数は `ignore` の
既定 (CPU 数) のまま。

### 1 ファイルの照合

原則は **「ファイルの大きさに比例する仕事は、バイト列の走査 1 回だけ」**。UTF-8 検証・小文字化・
タブ展開・`Vec<char>` 化はどれもファイル丸ごとにかけると走査 1 回ぶんの重さが積み上がるので、
当たった行 (か、避けられない時) だけに限る。

1. `File::open` → `take(8MB + 1)` で **ワーカーごとに使い回すバッファ** へ読む。溢れたら捨てる。
   stat はしない (10 万ファイル級では stat 1 回/ファイルが積み上がるうえ、open + read は結局要る)
2. 先頭 8KB に NUL → バイナリとして読まない (scanned にも数えない)
3. クエリに **空白があり** かつファイルにタブがある時だけ、タブ → 空白 4 に展開した写しを作る。
   VIEW の `/` は plain (展開済み) の上で探すので、生テキストでプリフィルタすると「空白 4 つ +
   foo」のクエリが `\tfoo` の行に当たらず、`/` と横断検索で結果が食い違う (Copilot レビューで
   指摘)。逆にクエリに空白が無ければ展開で一致が増減することは無いので写しは要らない。
   展開しても改行の位置は変わらないので、行の切り出しはこの写しの上でそのまま行える
4. **バイト列のまま** `find_at` で流す: needle の中で **最も稀なバイト** (`byte_frequency`、
   手書きの頻度表) の候補を `Candidates` で拾い、そこから逆算した位置だけ全長を突き合わせる。
   smart-case で大小無視の時は `eq_ignore_ascii_case` で比べる — **ファイルを小文字化した写しを
   作らない**。先頭バイトで探すと `usize` の `u` のような頻出文字で数十バイトごとに候補が立ち、
   走査の大半が突き合わせと再開で消える (ripgrep の memmem と同じ rare-byte の発想)。
   `Candidates` は x86_64 では SSE2 (基準命令セット・実行時判定なし・依存なし) で 32 バイトずつ
   一致ビットのマスクを作り、候補が密でもマスクのビットを順に消費するだけで再開する。それ以外の
   アーキテクチャは 8 バイトずつの SWAR。多バイト文字の途中のバイトで候補が立っても全長の一致で
   弾かれるので、char 境界の心配は要らない
5. 当たった行だけ `from_utf8_lossy` → `text::normalize` → `viewer::line_matches`
   (search_matches の行単位の中身をイテレータに切り出したもの) にかけ直す — これで列座標が
   VIEW の `/` と **完全に同じ規則** (plain の char index) になる。`take(残り枠)` で打ち切るので、
   minified な 1 行に短いクエリを投げても上限ぶんしか一致を確保しない。非 UTF-8 のファイルも
   行単位の lossy 変換で拾える (ファイル丸ごとを &str にしないので落とす理由が無い)

以前は `String::from_utf8_lossy` (検証 1 回) → 小文字化の写し → `str::find` だったが、
合成ツリー (2 万ファイル・120MB) の全走査で 80ms → 45ms になった (下記「測定」)。照合だけを
見ると、30MB のバッファで先頭バイト + SWAR が 13ms → rare-byte + SSE2 が 5ms。

### 上限と打ち切り

| 定数 | 値 | 理由 |
| --- | --- | --- |
| `MAX_HITS` | 5000 | 1 文字のクエリで結果がメモリと画面を埋め尽くさない。まとめ diff の 20000 行上限と同じ発想 |
| `MAX_HITS_PER_FILE` | 200 | minified な 1 行ファイル等が上限を独占しない |
| `MAX_FILE_BYTES` | 8 MB | 1 ワーカーが一時的に持つメモリの上限でもある |
| `MAX_LINE_CHARS` | 400 | 一覧に持つ 1 行の長さ。超える行はマッチの手前 40 文字から切り出し (`clipped`)。元の桁は `Hit::col` に別途持つ |

上限を跨いだファイルまでは送ってから `Quit` するので、実際のヒット数は 5000 を少し超えうる。
「ちょうど 5000」に切り詰める価値は無い (表示は `truncated at 5000` で足りる)。

### キャンセル

`Arc<AtomicBool>`。ワーカーはファイルごとに見て `WalkState::Quit` を返す。キャンセルされた
走査は `Done` も `Corpus` も送らない (途中までの一覧では「無い」と「まだ歩いていない」が
区別できない)。ただし読んだぶんは cache に重ねる (`replace(.., complete=false)`) ので無駄には
ならない。`GrepState::poll` は `Disconnected` でも走査中扱いを解くので、Done 無しで終わっても
UI が「searching...」のまま固まらない。

## 3. 状態 (mod.rs) の詳細

### 最小文字数

**2 文字未満では走査しない** (`MIN_QUERY_CHARS`、仕様)。1 文字は repo のほぼ全行に当たり、上限で
打ち切られた「先頭 5000 件」を見せるだけになるので、歩くコストに見合う結果が出ない。
`searchable()` が唯一の判定で、走査の起動・stale・タイトル・空表示の文言が全てこれを見る。

### デバウンス

打鍵ごとに repo 全体を歩き直さない。`push_char`/`backspace` は走っている走査を止め
(`cancel_job`)、`pending_since` を立てるだけ。実際に起こすのは `poll` (100ms tick) で
150ms 経過を見てから。**結果はこの時点 (spawn 直前) まで捨てない** — 打っている間も前の
結果が見えている方が落ち着いて読める (VSCode と同じ)。

その代わり、その間は `query` (入力中) と表示中の行を作ったクエリが食い違う。ヒットを開く時に
`query` を使うと「クエリ A の行にクエリ B の `/` を立てる」ことになるので、走査を起こした
時点のクエリを `result_query` に控え、`open_grep_hit` はそちらを使う。

### 結果の並び

ワーカーからの到着順はスレッドの都合で毎回違うので、`files` は **パス昇順** に保つ
(`partition_point` + `insert`)。平らにした `rows` は `poll` のたびに 1 回だけ作り直す
(ファイルの到着ごとには作らない。上限 5000 件なので tick あたり O(5000) で済む)。

既知の癖: 選択位置 `selected` は行 index なので、選択より前のパスのファイルが後から届くと
指している行がずれる。走査完了後は起きないので v1 では許容。気になるなら `(file path, hit)`
で選択を持ち直す。

### stale

FS 監視 (`App::on_tick` の `watcher.drain`) が 1 件でも変更を拾ったら `invalidate()`。
fv 上での保存 (`Ctrl+s`) も同じく `invalidate()` を呼ぶ — 監視を張れない環境では watcher
経由の印が来ないため (git status の `status_pending` と同じ経路):

- 走査中 → 止めて起こし直す (その走査は変更前後が混ざるため)
- 完了済み → `stale` を立てるだけ。タイトルに `stale` と出し、次に `Ctrl+f` で開いた時
  (`on_open`) に同じクエリで歩き直す

閉じている間に変更のたびに歩き直さないのは、「AI が高速に書き換え続ける」状況で repo 全体の
走査を連打しないため (FileIndex の stale と同じ考え方)。オーバーレイを **開いたまま** 変更が
来た場合も歩き直さず stale を出すだけで、明示的に閉じて開き直すか、クエリを打ち直す。

### 走査条件

`ScanOptions` (隠し項目・無視ファイル) はツリー・Finder・FS 監視と同じ 1 つを受け取る
(`set_options`)。ここがずれると「ツリーには出るのに grep に出ない」が起きる。

## 4. 座標系

ヒットの `col` は **plain (タブ展開済み) の char index**。VIEW の検索マッチ `viewer::Match`
と同じ座標系なので、`Viewer::locate_search(query, line, col)` は同じクエリで `/` を立て直し、
`(line, col)` が一致するマッチを現在位置にする。行だけで選ぶと同じ行の 2 つ目以降のヒットを
開いた時に `n` が「今開いたばかりの位置」へ進んでしまう。`start_col`/`end_col` は一覧側の
ハイライト用で、切り出した `hit.text` 内の座標 (切り出していなければ `col` と同じ)。

## 5. 測定

`cargo test --release -- --ignored grep_bench --nocapture` (component/grep/mod.rs の `bench`) が
合成ツリー (200 ディレクトリ × 100 ファイル × 120 行 = 2 万ファイル・約 120MB、半分はタブ
インデント) を `$TMPDIR/fv-grep-bench` に作り、6 種のクエリで **3 つの経路** の走査完了までの
最短時間を出す: `cold` (cache 無しの初回) / `walk` (歩き直すが変わっていないので読まない =
監視なし) / `corpus` (一覧をメモリ上で照合 = 監視あり)。ページキャッシュに乗った状態の値。
この環境 (4 コア) での推移:

| クエリ | 経路 | 初版 | stat 無し等 | バイト列走査 | cache: cold | cache: walk | cache: corpus |
| --- | --- | --: | --: | --: | --: | --: | --: |
| `zzzz` | 全走査・ヒット無し・大小無視 | 80 ms | 60 ms | 45 ms | 77 ms | 37 ms | 11 ms |
| `Zzzz` | 全走査・ヒット無し・大小区別 | — | 49 ms | 42 ms | 74 ms | 32 ms | 9 ms |
| `item_150_50_` | 全走査・1 ファイルだけ当たる | — | 60 ms | 45 ms | 81 ms | 32 ms | 11 ms |
| `needle3` 等 | 上限 5000 件で早期打ち切り | 5 ms | 5 ms | 5 ms | 7 ms | 4 ms | 3 ms |

cache 導入前の内訳 (同じツリーで walk だけ / + stat / + read / + 照合 を別々に測った):
walk 19ms・stat +4ms・read +19ms・照合 +2ms。走査の時間がそのまま syscall の時間だった。

- **corpus** が普段の打鍵で払う値。120MB を 4 スレッドで舐めて 10ms 前後 — メモリ帯域が
  上限で、これ以上は照合対象を減らす (trigram) しかない
- **walk** は監視が無い環境 (登録失敗・登録中) と構造変化の直後の値。read を払わないぶんだけ速い
- **cold** は初回の 1 度だけ。cache 導入前より 30ms ほど遅いのは stat と、120MB を新しく確保する
  page fault。2 回目以降で回収する

## 6. 手触りを測る時の物差し

大きい repo (10 万ファイル級) で見るのは 2 つ:

1. **最初のヒットまで** — ストリーミングが効いていれば走査完了を待たない
2. **走査完了まで** (タイトルの `N files scanned` が出るまで) — ページキャッシュに乗った
   2 回目以降が **1 秒を切るならインデックスは要らない**

初回の cold な走査はインデックスを作る時も同じコストを払うので比較対象外。

遅い時に疑う順番: (a) `.gitignore` が効いていない (`target/` や `node_modules/` を歩いている)
→ タイトルの scanned 数で分かる (b) 巨大な生成ファイル → `MAX_FILE_BYTES` (c) 本当に I/O
→ 2 段目 (content cache) へ。

## 7. 次の段 (やっていないこと)

- **trigram 等の転置インデックス**: corpus 経路はメモリ帯域が上限 (120MB で 10ms、線形)。
  1GB 級のツリーで打鍵ごとに 100ms を切りたくなったら、照合対象のファイルを絞る索引が要る。
  `spawn_corpus` の「一覧の全項目を舐める」を「索引が候補に挙げた項目だけ」に差し替える形
- **cache の上限を超えた時の入れ替え**: 256MB を超えたぶんは到着順で Uncached になり、どの
  ファイルが残るかは決定的でない。LRU 等は入れていない (超える repo で手触りを見てから)
- **正規表現**: 新規依存を足さない方針なのでリテラル一致のみ。`/` と同じ規則に揃えてある
- **AVX2**: `Candidates` は SSE2 (32 バイト/回)。AVX2 は実行時判定が要るので入れていない。
  corpus 経路はメモリ帯域が上限なので、入れても数値は動かないはず
- **結果のグループ表示** (ファイル見出し行を挟む): List の index と選択が合わなくなるので、
  ブランチ一覧と同じ理由で見送り。行ごとにパスを暗く出す方式で代用
- **ヒットの横スクロール**: 一覧の行はペイン幅で切れる。400 文字超の行はマッチ周辺を切り出す
  ので、幅より右にマッチが隠れるのは 40〜400 文字の範囲だけ
- **リプレース**: スコープ外 (fv は編集を「その場で手直し」に留める)
- **ツリーの選択追従**: Finder と同じく、ヒットを開いてもツリーの選択は動かさない
