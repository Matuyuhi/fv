# ワークスペース横断検索 (`Ctrl+f`) — 設計メモ

> **この文書は実装が落ち着いたら削除する前提の作業メモ**。恒久的に残す要約は
> `CLAUDE.md` の「ワークスペース横断検索」節にあり、そちらがコードと一緒に保守される。
> ここには「なぜこの形にしたか」「何を測ってから次へ進むか」「まだやっていないこと」を、
> CLAUDE.md には載せない粒度で書く。

## 0. 位置づけ

fv に「ファイルを跨いで探す」機能が無かった (`/` はファイル内限定)。インデックス設計の議論
(#index-design) の結論は次の通りで、この実装はその **1 段目** にあたる。

1. **インデックス無しの横断 grep を入れて、大きめの repo で手触りを確かめる** ← 今ここ
2. 足りなければ content cache (読んだ内容をメモリに残すだけ)
3. それでも足りなければ trigram 等の本物のインデックス
4. 永続化は最後

「インデックス無し」で先に入れる理由は、大きい repo で遅くなる主因が **照合ではなく走査と
読み込み** であり、そこは並列 walker + ストリーミングで作りを正しくすれば ripgrep 相当まで
行けるから。逆に、素朴な逐次 grep で入れてしまうと「遅いのはインデックスが無いからか、
作りが悪いからか」が切り分けられず、手触りの評価自体が成り立たない。

そのため最初から次の 4 点を満たす形で作った (どれか 1 つでも欠けると評価がずれる):

| 要件 | 実装 |
| --- | --- |
| 並列走査 | `ignore::WalkBuilder::build_parallel` (ripgrep と同じ walker、新規依存なし) |
| 結果のストリーミング + 打ち切り | 1 ファイル = 1 メッセージで channel へ流し、クエリが変わったら `AtomicBool` で止める |
| バイナリ・巨大ファイルの除外 | 先頭 8KB に NUL / 8MB 超は読まない |
| ヒット数の上限 | 全体 5000 件 / 1 ファイル 200 件で走査ごと打ち切り、タイトルに `truncated` |

## 1. 構成

```
src/component/grep/
  search.rs   走査本体 (背景スレッド側)。クエリ → Receiver<Message>
  mod.rs      GrepState: クエリ・デバウンス・結果 (パス順)・選択・stale
  view.rs     オーバーレイの描画 (Finder と同じ形。画面に映る行だけ ListItem を組む)
```

- `Mode::Grep` は **unit variant** で、状態は `App.grep: GrepState` に常駐する。
  Finder (`Mode::Finder(Finder)`) と違って Mode の中に持たせないのは、オーバーレイを閉じても
  走査を続け、次に開いた時に前回の結果をそのまま見せるため (大きい repo で同じクエリを
  何度も歩き直さない)。「状態の持ち主は誰か」という意味では `App.file_index` (Finder の候補
  の背景走査) と同じ側にいる
- キールーティングは `Mode::Finder` の直後 (app/keys.rs `on_key`)。開くキー `Ctrl+f` は
  `Ctrl+p` と同じ位置 (レーン・フォーカスを問わない、EDIT 中は届かない)
- ヒットを開く (`open_grep_hit`) は `open_selected` → `Viewer::locate_search` の 2 段。
  GIT レーンに居た場合は `enter_lane(0)` で VIEW に戻してから開く (open_selected は GIT だと
  diff を開いてしまうため)
- 描画は `shell::draw` から `grep::view::draw_grep(frame, &mut app.grep, full)`。
  「View は自分の状態しか受け取らない」規約通り `&App` は渡さない

## 2. 走査 (search.rs) の詳細

### スレッド構成

```
UI スレッド ── spawn() ──▶ ランナースレッド ── walker.run() ──▶ ワーカー N 本 (ignore が起こす)
     ▲                            │                                     │
     │  Receiver<Message>         │ Done (完了時 1 回)                    │ File (ヒットのある
     └────────────────────────────┴─────────────────────────────────────┘  ファイルごと 1 回)
```

`WalkParallel::run` は内部でワーカーを複数起こしたうえで **呼び出し側をブロックする** ので、
それ自体をもう 1 本のスレッドへ出している (UI スレッドを止めない)。ワーカー数は `ignore` の
既定 (CPU 数) のまま。

### 1 ファイルの照合

原則は **「ファイルの大きさに比例する仕事は、バイト列の走査 1 回だけ」**。UTF-8 検証・小文字化・
タブ展開・`Vec<char>` 化はどれもファイル丸ごとにかけると走査 1 回ぶんの重さが積み上がるので、
当たった行 (か、避けられない時) だけに限る。

1. `File::open` → `take(8MB + 1)` で **ワーカーごとに使い回すバッファ** へ読む。溢れたら捨てる。
   stat はしない (10 万ファイル級では stat 1 回/ファイルが積み上がるうえ、open + read は結局要る)
2. 先頭 8KB に NUL → バイナリとして読まない (scanned にも数えない)
3. クエリに **空白があり** かつファイルにタブがある時だけ、タブ → 空白 4 に展開した写しを作る。
   VIEW の `/` は plain (展開済み) の上で探すので、生テキストでプリフィルタすると「空白 4 つ +
   foo」のクエリが `\tfoo` の行に当たらず、`/` と横断検索で結果が食い違う (Copilot レビューで
   指摘)。逆にクエリに空白が無ければ展開で一致が増減することは無いので写しは要らない。
   展開しても改行の位置は変わらないので、行の切り出しはこの写しの上でそのまま行える
4. **バイト列のまま** `find_at` で流す: 先頭バイトの候補を `find_byte2` (8 バイトずつの SWAR
   判定、memchr2 相当・依存なし) で拾い、候補位置だけ全長を突き合わせる。smart-case で
   大小無視の時は `eq_ignore_ascii_case` で比べる — **ファイルを小文字化した写しを作らない**。
   クエリの先頭は ASCII か多バイト文字の先頭バイトなので、候補位置は常に char 境界
5. 当たった行だけ `from_utf8_lossy` → `text::normalize` → `viewer::line_matches`
   (search_matches の行単位の中身をイテレータに切り出したもの) にかけ直す — これで列座標が
   VIEW の `/` と **完全に同じ規則** (plain の char index) になる。`take(残り枠)` で打ち切るので、
   minified な 1 行に短いクエリを投げても上限ぶんしか一致を確保しない。非 UTF-8 のファイルも
   行単位の lossy 変換で拾える (ファイル丸ごとを &str にしないので落とす理由が無い)

以前は `String::from_utf8_lossy` (検証 1 回) → 小文字化の写し → `str::find` だったが、
合成ツリー (2 万ファイル・120MB) の全走査で 80ms → 45ms になった (下記「測定」)。

### 上限と打ち切り

| 定数 | 値 | 理由 |
| --- | --- | --- |
| `MAX_HITS` | 5000 | 1 文字のクエリで結果がメモリと画面を埋め尽くさない。まとめ diff の 20000 行上限と同じ発想 |
| `MAX_HITS_PER_FILE` | 200 | minified な 1 行ファイル等が上限を独占しない |
| `MAX_FILE_BYTES` | 8 MB | 1 ワーカーが一時的に持つメモリの上限でもある |
| `MAX_LINE_CHARS` | 400 | 一覧に持つ 1 行の長さ。超える行はマッチの手前 40 文字から切り出し (`clipped`)。元の桁は `Hit::col` に別途持つ |

上限を跨いだファイルまでは送ってから `Quit` するので、実際のヒット数は 5000 を少し超えうる。
「ちょうど 5000」に切り詰める価値は無い (表示は `truncated at 5000` で足りる)。

### キャンセル

`Arc<AtomicBool>`。ワーカーはファイルごとに見て `WalkState::Quit` を返す。キャンセルされた
走査は `Done` を送らない (送っても捨てるだけなので)。`GrepState::poll` は `Disconnected`
でも走査中扱いを解くので、Done 無しで終わっても UI が「searching...」のまま固まらない。

## 3. 状態 (mod.rs) の詳細

### 最小文字数

**2 文字未満では走査しない** (`MIN_QUERY_CHARS`、仕様)。1 文字は repo のほぼ全行に当たり、上限で
打ち切られた「先頭 5000 件」を見せるだけになるので、歩くコストに見合う結果が出ない。
`searchable()` が唯一の判定で、走査の起動・stale・タイトル・空表示の文言が全てこれを見る。

### デバウンス

打鍵ごとに repo 全体を歩き直さない。`push_char`/`backspace` は走っている走査を止め
(`cancel_job`)、`pending_since` を立てるだけ。実際に起こすのは `poll` (100ms tick) で
150ms 経過を見てから。**結果はこの時点 (spawn 直前) まで捨てない** — 打っている間も前の
結果が見えている方が落ち着いて読める (VSCode と同じ)。

その代わり、その間は `query` (入力中) と表示中の行を作ったクエリが食い違う。ヒットを開く時に
`query` を使うと「クエリ A の行にクエリ B の `/` を立てる」ことになるので、走査を起こした
時点のクエリを `result_query` に控え、`open_grep_hit` はそちらを使う。

### 結果の並び

ワーカーからの到着順はスレッドの都合で毎回違うので、`files` は **パス昇順** に保つ
(`partition_point` + `insert`)。平らにした `rows` は `poll` のたびに 1 回だけ作り直す
(ファイルの到着ごとには作らない。上限 5000 件なので tick あたり O(5000) で済む)。

既知の癖: 選択位置 `selected` は行 index なので、選択より前のパスのファイルが後から届くと
指している行がずれる。走査完了後は起きないので v1 では許容。気になるなら `(file path, hit)`
で選択を持ち直す。

### stale

FS 監視 (`App::on_tick` の `watcher.drain`) が 1 件でも変更を拾ったら `invalidate()`。
fv 上での保存 (`Ctrl+s`) も同じく `invalidate()` を呼ぶ — 監視を張れない環境では watcher
経由の印が来ないため (git status の `status_pending` と同じ経路):

- 走査中 → 止めて起こし直す (その走査は変更前後が混ざるため)
- 完了済み → `stale` を立てるだけ。タイトルに `stale` と出し、次に `Ctrl+f` で開いた時
  (`on_open`) に同じクエリで歩き直す

閉じている間に変更のたびに歩き直さないのは、「AI が高速に書き換え続ける」状況で repo 全体の
走査を連打しないため (FileIndex の stale と同じ考え方)。オーバーレイを **開いたまま** 変更が
来た場合も歩き直さず stale を出すだけで、明示的に閉じて開き直すか、クエリを打ち直す。

### 走査条件

`ScanOptions` (隠し項目・無視ファイル) はツリー・Finder・FS 監視と同じ 1 つを受け取る
(`set_options`)。ここがずれると「ツリーには出るのに grep に出ない」が起きる。

## 4. 座標系

ヒットの `col` は **plain (タブ展開済み) の char index**。VIEW の検索マッチ `viewer::Match`
と同じ座標系なので、`Viewer::locate_search(query, line, col)` は同じクエリで `/` を立て直し、
`(line, col)` が一致するマッチを現在位置にする。行だけで選ぶと同じ行の 2 つ目以降のヒットを
開いた時に `n` が「今開いたばかりの位置」へ進んでしまう。`start_col`/`end_col` は一覧側の
ハイライト用で、切り出した `hit.text` 内の座標 (切り出していなければ `col` と同じ)。

## 5. 測定

`cargo test --release -- --ignored grep_bench --nocapture` (component/grep/mod.rs の `bench`) が
合成ツリー (200 ディレクトリ × 100 ファイル × 120 行 = 2 万ファイル・約 120MB、半分はタブ
インデント) を `$TMPDIR/fv-grep-bench` に作り、5 種のクエリで走査完了までの最短時間を出す。
ページキャッシュに乗った 2 回目以降の値。この環境 (4 コア) での推移:

| クエリ | 経路 | 初版 | stat 無し + バッファ使い回し + 写しの条件付け | バイト列走査 |
| --- | --- | --: | --: | --: |
| `zzzz` | 全走査・ヒット無し・大小無視 | 80 ms | 60 ms | 45 ms |
| `Zzzz` | 全走査・ヒット無し・大小区別 | — | 49 ms | 42 ms |
| `item_150_50_` | 全走査・1 ファイルだけ当たる | — | 60 ms | 45 ms |
| `needle3` 等 | 上限 5000 件で早期打ち切り | 5 ms | 5 ms | 5 ms |

大小無視と区別の差がほぼ消えたのは、小文字化の写しが要らなくなったため。残りはほぼ
open + read の syscall で、これ以上はインデックス (content cache) の領分。

## 6. 手触りを測る時の物差し

大きい repo (10 万ファイル級) で見るのは 2 つ:

1. **最初のヒットまで** — ストリーミングが効いていれば走査完了を待たない
2. **走査完了まで** (タイトルの `N files scanned` が出るまで) — ページキャッシュに乗った
   2 回目以降が **1 秒を切るならインデックスは要らない**

初回の cold な走査はインデックスを作る時も同じコストを払うので比較対象外。

遅い時に疑う順番: (a) `.gitignore` が効いていない (`target/` や `node_modules/` を歩いている)
→ タイトルの scanned 数で分かる (b) 巨大な生成ファイル → `MAX_FILE_BYTES` (c) 本当に I/O
→ 2 段目 (content cache) へ。

## 7. 次の段 (やっていないこと)

- **content cache**: 読んだ内容を `(path, mtime, size)` キーでメモリに残し、`watch::Change`
  の path で該当分だけ捨てる。走査と読み込みが消えるので、メモリ上の照合だけなら 10 万
  ファイルでも十分速いはず。`search.rs::spawn` の中だけを差し替えれば済む形にしてある
  (`GrepState` は「クエリを渡すと `Message` が流れてくる」以上を知らない)
- **正規表現**: 新規依存を足さない方針なのでリテラル一致のみ。`/` と同じ規則に揃えてある
- **SIMD の memchr**: `find_byte2` は 8 バイト SWAR。ripgrep の memchr クレート (AVX2) には
  及ばないが、依存を足さない範囲ではこれが上限。効いてくるのは巨大ファイルが多い repo だけ
- **結果のグループ表示** (ファイル見出し行を挟む): List の index と選択が合わなくなるので、
  ブランチ一覧と同じ理由で見送り。行ごとにパスを暗く出す方式で代用
- **ヒットの横スクロール**: 一覧の行はペイン幅で切れる。400 文字超の行はマッチ周辺を切り出す
  ので、幅より右にマッチが隠れるのは 40〜400 文字の範囲だけ
- **リプレース**: スコープ外 (fv は編集を「その場で手直し」に留める)
- **ツリーの選択追従**: Finder と同じく、ヒットを開いてもツリーの選択は動かさない

## 8. 動作確認

```sh
cargo test grep                          # 走査 (座標・smart-case・除外) と状態 (stale/再走査)
cargo preview grep grep-jump             # オーバーレイと、Enter で飛んだ直後
```

実機では `cargo run --release -- <大きい repo>` → `Ctrl+f` → 数文字打つ → タイトルの
`searching...` → `N files scanned` の推移を見る。
